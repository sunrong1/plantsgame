# plants-game - Epic Breakdown

## Overview

本文档将 GDD 的设计需求与 Game Architecture 的技术决策，拆解为可独立验收的 story。
每个 story 是一个可在单个 context window 内完成的实现单元。

**开发原则：垂直切片优先。** 首个 Epic 用一个完整教材单元端到端跑通全部系统，
先验证孩子愿不愿意玩，再投入内容量生产。旧版本走功能广度优先的路线，历经 5 个
大版本仍只积累 9 张词图，该路线已被证伪。

**目标平台：** 华为 Android 平板浏览器，竖屏。
**技术栈：** Vue 3.5 + Vite 8 + TypeScript strict + Vitest 5，**无游戏引擎**（DOM + CSS）。

## Requirements Inventory

### Functional Requirements

**A. 发音与音频（支柱 1 的入口）**

```
FR1:  每题卡面出现时自动播放一次 TTS 朗读；卡面可点击无限次重听，重听无任何代价或次数限制
FR2:  「开始游戏」点击处理器内同步完成全部音频解锁：AudioContext.resume() + TTS preheat（volume=0 空 utterance）
      + BGM buffer 预解；三者之间不允许任何 await
FR3:  speechSynthesis.cancel() 仅在 speechSynthesis.speaking === true 时调用
FR4:  TTS 不可用或播放失败时自动降级为预置录音，走统一的 playPronunciation(text) 接口；
      降级通路必须固定在架构层，不得是临时 if
FR5:  TTS 播放失败绝不阻断回合流转 —— 支柱 1 的唯一入口挂掉时游戏仍须能进行
FR6:  音效共 7 个事件：答对、答错、建塔、僵尸死亡、僵尸抵达（掉心）、通关、失败；
      每个音效必须对应一个明确事件，不做装饰性音效
FR7:  答错音效为短促下行音且不刺耳（学习反馈，不是惩罚音）
FR8:  战斗循环 BGM 单曲循环
```

**B. 三种卡型与答题（支柱 1、支柱 3）**

```
FR9:  单词卡 —— TTS 播单词（dog），孩子从图片选项中选出对应图片（听音 → 识物）
FR10: 关键词卡 —— TTS 播完整句子（I have a ball for my dog.），孩子从句中关键词的文字卡中选出（听句 → 提取信息）
FR11: 回应卡 —— TTS 播问句或短语（How are you / good morning），孩子从英文文字卡中选出正确回应（听问 → 应答）
FR12: 短语归入回应卡，不单独成卡
FR13: 选项卡带英文文字（关键词卡、回应卡），孩子选择时同时在读；单词卡选项为纯图片
FR14: 三种卡型的判定逻辑唯一且共享 —— 均为 n 选 1、唯一正确项；
      卡型差异只在数据（选项是图片还是文字）与渲染，不在判定代码
FR15: 三种卡型构成难度阶梯：单词卡 < 关键词卡 < 回应卡
FR16: 「唯一正确项」为 schema 级约束（内容校验时保证），不是运行时判断
FR17: 选项数量随卡型与关卡递进，早期关卡可从 2 个选项起步
FR18: 选择提交到反馈呈现 ≤ 100ms
FR19: 单元 1 须至少各含一道单词卡、关键词卡、回应卡，以验证完整卡型链路
```

**C. 答题结算（支柱 1 → 支柱 2 的耦合点）**

```
FR20: 答对 → 阳光 + 该单元档位的增量（单元 1-4 为 +50），并解锁该词对应的塔卡
FR21: 答错 → 阳光不变（不扣不加）、无塔卡可用、该词留在本局题单内重复出现直到答对为止
FR22: 答对的题不再出现；本局题单在一局内固定不变
FR23: 答对解锁的塔只能种该词对应的塔；答对不自动消灭僵尸 —— 塔是唯一能杀死僵尸的东西
FR24: 失败重打时：心数重置为 3、阳光重置为初始值、本局题单内容不变
FR25: 每回合开始时，该题对应的僵尸从右侧入场 —— 答对与答错都入场，
      区别只在答对会给阳光和塔
```

**D. 建造与放置（支柱 2）**

```
FR26: 两步放置 —— 点卡片（卡片高亮表示选中）→ 点战场空格 → 塔种下
FR27: 建造阶段扣除该塔型的造价；阳光不足时卡片变灰不可点
FR28: 已选中的卡片在种下后消失，或点击空白处 / 再次点击卡片取消
FR29: 未选中卡片时点击格子无效（防误触靠选中态高亮，不靠输入延迟）
FR30: 已占用格子不再响应
FR31: 不做铲除、不做拖拽、不做建造模式；种下即不可撤回
FR32: 选中卡片时显示该塔的射程覆盖范围 —— 射程不可见会造成「为什么它没打到我」的困惑，
      对 6 岁半是一次挫败就可能让他放弃使用这个塔
FR33: 手牌不因建造而消失 —— 同一张已解锁的塔卡可反复建多株
```

**E. 战斗结算**

```
FR34: 三种塔型，首版数值（造价 / 每回合伤害 / 射程）：
      直射型 50 / 50 / 射程 3 格（单体）；减速型 50 / 25 / 射程 3 格（单体 + 减速 50%）；范围型 75 / 60 / 同行 3 格
FR35: 减速 50% 持续 3 回合，被同一座塔重复命中则刷新而非叠加
FR36: 塔每回合攻击射程内最靠近房子的僵尸（列号最小者）；射程内无僵尸则本回合不攻击
FR37: 射程是单向的 —— 僵尸只从塔的右侧接近，永不从左侧进入；
      实现时按「射程内每回合命中一次」计算，不得用「射程×2 ÷ 速度」推算攻击窗口
FR38: 范围塔攻击范围 = 以塔所在列为中心、沿僵尸所在行（固定第 3 行）的 [列-1, 列, 列+1] 共 3 格。
      不是半径 2 的圆（那在同行横跨 5 格，严重超模）
FR39: 战斗数值只能读 tower.towerType，永远不读 tower.wordId —— 否则同一塔型因绑定词不同而表现不同，
      平衡验证全部失效
FR40: 无塔的升级机制 —— 答对即解锁，买下即可用
FR41: 范围塔在仅 1 只僵尸时严格劣于直射塔（60<100 且 75>50），只有僵尸堆积时才胜出。
      不得出现「买来就赢」的退化策略
FR82: 【补充于 [IR]】塔跨回合持久存在 —— 回合结束结算后，已建塔保留在场，不被清空；
      只有一局结束时战场才整体清空（见 FR51）。
      这是 GDD「接受失败门槛偏高」这一取舍的前提：塔若每回合消失，
      答对一题换来的塔当回合就没了，GDD 实测的「开局连错 7 题 = 失败」门槛彻底失效。
      ⇒ 该性质必须有断言，不能只作为论据被引用（Story 2.2 / 3.2 / 3.3 都拿它当论据）
```

> **编号说明：** FR82 为 `[IR]` 评审后补入，物理位置在 E 组（战斗结算）内但编号接续于 FR81。
> 重新编号会波及覆盖映射表与 32 个 story 的 📎 行，收益不抵风险，故保留跳号。

**F. 僵尸与战场**

```
FR42: 僵尸为通用敌人，不承载题目内容，一次一个（逐只出现而非成群），
      因果一一对应，避免 6 岁半无法分辨哪个僵尸对应哪题
FR43: 僵尸首版数值：100 血、每回合前进 2 格、固定中间行（第 3 行）、自第 9 列入场
FR44: 僵尸从入场到抵达房子 = 4 回合（第 9→7→5→3→1 列，越过第 1 列即抵达）
FR45: 只有塔能杀死僵尸；血量归零即死亡
FR46: 战场为 5 行 × 9 列网格；僵尸固定走中间行，塔可种在任意空格
FR47: 塔的射程形状与僵尸行无关 —— 种在上下相邻行的塔也能打到中间行的僵尸，
      「种在哪」因此是真实决策
```

**G. 回合流程与胜负**

```
FR48: 一题 = 一回合。回合阶段依次为：等答题 → 结算奖励 → 等建造 → 结算战斗 → 回合结束
FR49: 回合结束结算顺序固定：所有塔各攻击射程内目标一次 → 所有存活僵尸前进 2 格 →
      走到房子的僵尸消失并丢 1 颗心
FR50: 心初始 3 颗；僵尸抵达房子丢 1 心；3 心耗尽 = 本局失败
FR51: 一局 = 一场独立战斗（约 10 题 = 10 回合）；战场状态在局末清空，不跨局保留
FR52: 一关 = 若干局；单元内全部内容均需考核，不做删减；全部完成才算过该单元
FR53: 回合内的两处无限等待（等选卡、等建造）必须属于 State —— 存档与合法性校验都依赖这一点
FR54: reducer 按阶段拒绝非法 action（如 PLACE_TOWER 仅在建造阶段合法）
```

**H. 进度与持久化**

```
FR55: 关卡单位 = 教材单元，一个单元一关；内容范围为一年级全年两册，关卡总数约 16-20 关
FR56: 进度可见 —— 孩子随时能看到自己读到哪了（如「第 3 单元 · 21/60」，60 = 该单元待答题总数）
FR57: 进度持久化（硬需求）—— 一关跨多次游戏，必须支持断点续学，精确恢复到上次答到的那一题
FR58: 进度只增不减 —— 因「词不过关就不出这一局」成立，单元内所有词最终必然答对
FR59: 跨单元线性推进 —— 单一进度线，无多单元并行，无选关自由
FR60: 进度与对局是两套生命周期独立的持久化：progress 只增不减跨局累积，currentGame 局末清空。
      战场与进度混在一起会在局末丢掉「21/60」
FR61: 存档带 schemaVersion；读取时校验版本，不匹配则安全降级（提示重新开始，不得崩溃）
```

**I. 经济**

```
FR62: 阳光是全局唯一经济资源，只在答对时增长，建造时必须花掉；
      余额可增可减（答对 +增量，建塔 −造价），累计所得只增不减
FR63: 阳光按关卡段递增（单元 / 初始 / 答对增量 / 造价）：
      1-4 → 0 / +50 / 50,50,75；5-10 → 50 / +75 / 75,75,110；11-20 → 100 / +100 / 100,100,150
FR64: 【硬约束】全程保持「单次答对所得阳光 ≥ 最低塔造价」，
      否则孩子可能答对了却买不起塔，支柱 1 与支柱 2 的耦合会断成两截
FR65: 僵尸被消灭不额外产出阳光（无战利品）
FR66: 阳光不出现在学习评价中 —— 无「阳光总数」分数，不比较不同单元的阳光存量
```

**J. 内容数据与美术资产**

```
FR67: 单元内容为 JSON 文件 + Zod schema + 独立校验脚本（录入是数据工作，不是编程工作）
FR68: 内容校验脚本必须在提交前抓出：词图文件缺失或命名不符、塔绑定指向不存在的塔型、
      选项中混入其他单元的词条、卡型与选项形态不符（单词卡选项应为图片引用，
      关键词/回应卡应为英文文本）、卡面 TTS 文本为空
FR69: 词图格式为 SVG，正方形画布 viewBox 统一；文件名 = 词条 id（public/assets/words/unit-NN/<id>.svg）
FR70: 美术资产按塔型制作（2-3 套），不按词制作 —— 词汇不产生美术成本，只有单词图片产生美术成本
FR71: 僵尸美术一套通用敌人，扁平矢量
FR72: 题面与选项的文字渲染走字体，不做美术
FR73: 词图按单元增量补充；起步范围为一个单元（约 15-30 词，对应 15-30 张图）
FR74: 词图按单元预取（进入单元前完成，战斗中零加载停顿），同时后台预取下一单元
```

**K. 难度阶梯（跨关）**

```
FR75: 早期关卡以单词卡为主，逐步引入关键词卡与回应卡，构成难度曲线
FR76: 战斗层不贡献难度 —— 僵尸强度与路径复杂度在各关保持一致，
      游戏的新鲜感全部来自词汇，变化由卡型分布与词汇本身（教材顺序）承载
```

**L. 平台与交互**

```
FR77: 纯触摸输入，无长按、无拖拽；所有可点区域须大于儿童手指可点范围
FR78: 任何点击应在 100ms 内给出视觉反馈
FR79: 语音浮层不得遮挡可交互的战场区域（源自旧版本已知问题）
FR80: 资源栏与战场在竖屏高分辨率下须保持可用的间距（源自旧版本已知问题）
FR81: 平板竖屏为主要形态
```

**M. 范围外（v1.0 明确不做，防止拆解时溢出）**

```
OUT-OF-SCOPE-1: 元进度系统 —— 无星星、图鉴、连对 streak、分数排行（内容即进度）
OUT-OF-SCOPE-2: 塔的升级机制
OUT-OF-SCOPE-3: 主动技能 / 特殊能力 —— 无铲除、无冰冻、无空袭
OUT-OF-SCOPE-4: 战斗层难度变化 —— 僵尸强度、路径复杂度各关一致
              ⚠️ [IR] 2026-10-12 补充：本条排除的是「各关之间的差异」，
                不排除「因战斗疲劳而全局调整」—— 那条路径由 Story 3.8（条件 story）承接。
OUT-OF-SCOPE-5: 多单元并行 / 选关自由
OUT-OF-SCOPE-6: 公开发布所需的适配
OUT-OF-SCOPE-7: 产出型学习环节（跟读、复述、发音比对）—— 当前机制为辨认型
OUT-OF-SCOPE-8: 无尽模式与波次无限缩放 —— 内容总量有界，通关即终点
OUT-OF-SCOPE-9: 遥测与埋点 —— 不设分析系统
```

### NonFunctional Requirements

```
NFR1:  战场渲染在目标平板上稳定 60 FPS，单局全程无掉帧
NFR2:  冷启动到可交互 ≤ 3 秒（首屏）
NFR3:  单元切换加载 ≤ 2 秒；当前单元词图已缓存时 ≤ 0.5 秒
NFR4:  TTS 朗读点击后 500ms 内起声，不得有可感知卡顿
NFR5:  答题反馈延迟（选择提交 → 反馈呈现）≤ 100ms
NFR6:  连续游玩 30 分钟无明显内存增长
NFR7:  core/ 零 DOM、零 Vue —— 由 tsconfig.core.json 的 lib 不含 DOM 在类型层面强制，
       配 ESLint no-restricted-imports。边界从「约定」变为「不可能违反」
NFR8:  组件内不得出现战斗规则计算 —— 只能读 state 或 dispatch action，答案只有一个来源 core/
       （⚠️ AI 最容易漂移的一条，CR 须重点检查）
NFR9:  战斗数值只读 tower.towerType，永远不读 wordId
NFR10: 副作用只在 app/effects-runner.ts 执行 —— 组件内禁止 watch 后自行播音效
NFR11: 动画时长写在 CSS，不写在 TS；动效为「状态变化 → 切 class → CSS transition」，
       禁止 JS 补间库与逐帧 setInterval/rAF
NFR12: 错误分层 —— 逻辑层必须 throw 禁止 catch（吞掉不变量违反会让数值静默漂移）；
       内容加载失败即拒绝进入游戏；运行时（TTS/图片/音频/存档）记录并静默降级，绝不阻断回合
       ⇒ 「/存档」为 [IR] 补充：GDD 原文只列了 TTS/图片/音频，但断点续学是硬需求（gdd.md:412），
         存档写入失败同样必须降级为内存态而非抛错。本补充不扩大功能范围，只明确失败路径
NFR13: 【压倒性原则】孩子面前永不出现技术错误 —— 6 岁半看到报错即为死局
NFR14: 日志仅 console（无遥测）；每条带模块前缀 [core]/[tts]/[save]/[content]；
       禁止在渲染路径打日志；DEBUG 级经 import.meta.env.DEV 门控
NFR15: 内容改动后必须跑 npm run validate:content（提交前钩子）
NFR16: 测试全部置于 tests/，按模块分文件；core/ 目录内不出现 .test.ts
NFR17: 不得为组件编写业务逻辑测试 —— 组件测试仅覆盖渲染与事件转发，
       以及逻辑层覆盖不到的两处：射程预览形状渲染、阶段切换的 UI 表现
NFR18: TypeScript strict: true
NFR19: 目标设备为华为 Android 平板浏览器；Node ≥ 22.12（Vitest 5 要求）
NFR20: 部署为 HTTPS 静态托管 —— Service Worker 仅在安全上下文注册，
       局域网 IP 下离线化会静默失效
NFR21: 缓存版本管理 —— 构建产物带内容哈希；激活新 SW 时提示「下次启动生效」；
       不得在游戏进行中强制刷新
NFR22: 调试 UI 不得进入生产构建 —— import.meta.env.DEV 门控，且不做成可路由到达的页面
```

### Additional Requirements

来自 Architecture 的技术要求，逐条影响实现。

```
AR1:  Architecture 未指定任何 starter 模板 —— Epic 1 的第一个 story 必须从零搭建工程脚手架：

AR3:  目录结构按架构文档的 Project Structure 建立：
     src/core/（纯逻辑）、src/content/、src/services/（DOM 副作用）、src/app/（Vue 绑定）、
     src/components/{battle,quiz,hud,debug}/、src/views/、src/styles/、
```

### Story 1.4: 回合状态机与题单

As a 孩子,

**Given** 一道题被判为答对
**When** 结算

**Then** 阳光**不变**（不扣不加）、无塔卡可用、该词留在题单内

**Given** 僵尸被塔打死

**And** 减速被同一座塔重复命中时**刷新**而非叠加（3 回合不会变成 6 回合）
**And** 回合结束结算后**已建塔保留在场**，不被清空（FR82）—— 只有一局结束时战场才整体清空

### Story 1.13: 音效与 BGM 接入

As a 孩子,
I want 每次答对、答错、建塔、僵尸倒下都有对应的声音,
So that 就算一时看不懂画面，我也知道刚才发生了什么。

**Acceptance Criteria:**

**Given** `src/core/effects.ts`
**When** 实现 `runEffects(action, prev, next)`

**Given** `src/app/effects-runner.ts`
**When** `applyAction` 执行
**Then** 顺序固定且可测：`reduce` → `runEffects` → 更新 state → 执行副作用
**And** **组件内禁止 `watch` 状态变化后自行播音效** —— 那会造成同一事件被播多次，且无法测试（`[CR]` 评审项）

**Given** 游戏中的七个事件

**And** **音效的唯一职责是帮助孩子理解因果，不做装饰性音效**

**Given** 音频已解锁
**When** 进入战斗
**Then** BGM 单曲循环播放

**And** 所有动画时长写在 CSS，不写在 TS；动效为「状态变化 → 切 class → CSS transition」，**不引入 JS 补间库**，不用 `setInterval`/rAF 逐帧改样式
**And** `runEffects` 的副作用触发逻辑有对应测试

---

**⚠️ 音频资源缺失 —— 静默跳过，绝不阻断回合（NFR12 / NFR13）。**

**Given** 某个音效或 BGM 文件加载失败（404、解码失败、或离线时不在缓存中）
**When** `effects-runner` 执行到对应的副作用
**Then** **静默跳过该音效** —— 记 `WARN` 日志（前缀 `[tts]`/`[audio]`）后直接继续
**And** **不抛错、不弹窗、不阻断回合流转** —— 音效没了只是少一条听觉线索，游戏本身照常进行
**And** 同一资源后续再次触发时**不重复请求**（失败即标记，跳过重试）

**Given** 音频会话本身不可用（`AudioContext` 创建失败或被浏览器拒绝）
**When** 需要播放任意音频
**Then** 全部音频静默跳过，游戏**完全可玩** —— TTS 已由 Story 1.2 降级为预置录音，

**And** 暴露一个**可查询的降级标志**（如 `audioService.silent === true`）与失败原因

### Story 1.14: 存档与断点续学

As a 孩子,
I want 玩到一半被叫走、回来还能接着玩,
So that 我不用每次都从头开始。

**Acceptance Criteria:**

**Given** 存档格式
**When** 查看 `SaveFile`
**Then** 结构为 `{ schemaVersion, savedAt, progress: { currentUnitIndex, masteredWordIds }, currentGame: State | null }`
**And** **`progress` 与 `currentGame` 是两套生命周期独立的数据，不可合并**

**Given** 存的是完整 state 而非「答对记录」
**When** 恢复对局
**Then** 阳光、心数、场上僵尸、已建塔、当前阶段全部还原
**And** 因为 state 本身是可序列化的普通对象，断点续学**不需要任何特殊设计**
**And** 若只存答对记录，恢复出的局面实际会变成重新开局 —— 与需求直接矛盾

**Given** 玩法进行中
**When** 每个回合结束
**Then** 写一次存档（约 20-30 秒间隔）—— 足够密集以满足断点续学，又不至于每次点击都写

**Given** 存档的 `schemaVersion` 与当前版本不匹配
**When** 读取
**Then** 安全降级：提示重新开始，**不得崩溃**（孩子面前永不出现技术错误）

**Given** 一局结束
**When** 战场被清空
**Then** `currentGame` 置为 `null`，**`progress` 不受影响**
**And** 否则局末清空战场时会连带把「第 3 单元 · 21/60」一起清掉

**And** 中途退出重进，能**精确恢复到上次答到的那一题**，包括当前处于 `awaiting-build` 的局面
**And** 存档写入记 `INFO` 日志（前缀 `[save]`）

---

**⚠️ 存档写入失败 —— 降级为内存态，游戏继续可玩（NFR12 / NFR13）。**

**Given** `localStorage` 写入失败（配额满、无痕/隐私模式禁用存储、存储被系统清理）
**When** 每回合结束触发存档
**Then** 捕获异常，降级为**内存态**：本局继续正常玩，**不阻断任何一回合**
**And** 记 `WARN` 日志（前缀 `[save]`），**不在孩子面前弹出任何错误**
**And** **不做任何静默丢弃** —— 明确区分「写成功了」与「这次没存上」两种状态

**Given** 处于内存态
**When** 查询存档服务状态
**Then** 暴露一个**可查询的降级标志**（如 `saveService.degraded === true`）与最近一次失败原因
**And** 该标志**由本 story 产出、由 Story 1.16 的调试面板消费** ——
**本 story 不负责 UI**，不得提前引用尚未实现的调试面板组件（`[IR]` 评审要求：不得引入前向依赖）
**And** 在 Story 1.16 完成前，该状态**仅通过日志与返回值暴露**，不呈现在任何画面上

**Given** 游戏结束时仍未成功写入
**When** 退出
**Then** 孩子失去的只是**本次会话**的进度；上一次成功写入的存档仍可读取，**不损坏既有存档**
**And** 存档文件损坏时同样安全降级为「从上一个单元重新开始」，而非崩溃或卡死

> **为什么这条不能省：** `localStorage` 在平板浏览器上因隐私模式、
> 存储配额、厂商清理策略而写入失败是**常见场景而非边缘场景**，
> 而「断点续学」被 GDD 列为**硬需求**（gdd.md:412）—— 它失效时孩子会直接损失进度。
>
> 但失效的**表现方式**必须可控：孩子面前出现一个存储报错弹窗，
> 比孩子不知道「关掉就丢了」要糟糕得多 —— 前者让他以为游戏坏了，后者只是接着玩。
> 因此提示只给家长，游戏本身继续。

**📎 覆盖：** FR57、FR60、FR61、**NFR12**、NFR13、AR14–AR16

### Story 1.15: 关卡流程：通关、失败与推进

### Story 2.1: 词图产能验证

As a 家长,
I want 在投入 300 张插画之前,先知道这件事到底做不做得完,
So that 我不会像旧版本那样,花 5 个大版本只做出 9 张图然后烂尾。

**Acceptance Criteria:**

**Given** 全年两册按 200-400 词估算（GDD 的数字，**本 story 会先校准它再采信**，见下）
**When** 按 20 分钟/张估算纯绘图工时
**Then** 得到 **66-133 小时**，不含返工与返工比例
**And** 该数字与历史证据并列记录：旧版本（tag `legacy-v5.x-final`）历经 5 个大版本，
`public/assets/` 仅积累 9 张图 —— 这是旧项目停滞的直接原因

**Given** 单元 1 已跑通（Epic 1）
**When** 选取 3-5 个代表性词条实画
**Then** 记录每张的**实际耗时**（含返工），得出现实均值而非估算值
**And** 产出样本覆盖三种难度：单一名词、需要组合的元素、多元素场景

**⚠️ 先校准基数，再估工时 —— 200-400 这个数字本身可能是错的。**

**Given** 上面两张估算互相对不上
**When** 对照：「约 15-30 张/单元 × 全年约 18 单元」= **270-540 张**，
      而「全年 200-400 词 → 200-400 张」= 上限 400
**Then** 差异必须**先查清再算工时**：200-400 是**总词数**，
      但**只有单词卡的词需要图片**（关键词卡与回应卡的选项是文字，FR13）——
      GDD 从未说明这个比例，两组数字才各自成立却对不上
**And** 本 story 的第一项实测工作因此是：**统计单元 1 中需要图片的词条实际占比**，
      用实测比例 × 全书总词数，得出**真实图片总数**，替换 200-400 这个估算基数
**And** 若实测比例高于 60%，图片数将突破 400 张 —— 那意味着按 20 分钟/张
      工时**成比例上浮**，「做不完」的结论可能在这次统计后就已成立，
      不必等到实画 3-5 张之后（`[IR]` MEDIUM-7）

**Given** 有了实测单位耗时与校准后的图片总数
**When** 评估三条杠杆
**Then** 逐条给出可行性与省时幅度，并产出一个**带数字的决策**：
1. **图片复用规则** —— 哪些词可共用同一张图（如 `dog` / `a dog` / `my dog`）
2. **程序化生成方案** —— 是否与扁平矢量风格兼容（SVG + 统一色板是必要条件）
3. **缩小内容范围** —— 全年两册 → 单册，或按单元裁剪
**And** 决策须显式对比三个选项在「全书可玩」与「半年内做完」两个维度上的取舍

**And** 决策产出后，Story 2.5–2.8 的批次规模按该结论确定（可能是每批 5-6 单元，也可能是缩到上册）
**And** 该决策记录在项目知识库 `docs/`，供 `[CE]`/`[IR]` 追溯

**⚠️ 本 story 允许得出「做不完」的结论。** 若结论是全年两册做不完，
则缩到上册并接受内容范围收窄 —— 这比投 100 小时后停在半途更划算。

### Story 3.7: 全流程最终验收

As a 家长,
I want 儿子从头打到尾,我没在任何一关觉得他卡住或者不想玩,
So that 我可以放心地把这个游戏交给他自己想玩多久就玩多久。

**Acceptance Criteria:**

**Given** 全部调优完成
**When** 孩子在目标平板上连续试玩全书
**Then** **不再出现挫败点或卡关** —— 这是本 Epic 的完成判据
**And** 每关通关后都有明确的正反馈，孩子知道「打完了这一段」

**Given** 全部调优完成
**When** 回归全部质量项
**Then** `npm run test` 全绿
**And** `npm run validate:content` 通过
**And** `npm run balance-sim` 输出与锁定的断言一致
**And** 断点续学仍精确；进度仍只增不减；局末清空不影响进度

**Given** 全部质量项通过
**When** 检查是否仍然守住边界
**Then** **无元进度系统**被引入（星星、图鉴、连对 streak、分数排行）——

**And** **战斗层在各关保持一致** —— 未在打磨过程中偷加难度变化
      （唯一可能改变它的是条件 story 3.8；本story须确认它**未被触发或已单独确认**）
**And** **无铲除、无拖拽、无升级、无技能**被引入
**And** 未引入遥测或埋点 —— 指标以直接观察为准

**Given** 边界守住

### Story 3.8: ⚠️ 条件 story —— 战斗疲劳重评（触发才开，不触发则销项）

As a 开发者,
I want 孩子在战斗层出现疲劳时有一条已定的处置路径,
So that 真到了那一天不必临场拍脑袋 —— 而临场拍脑袋的结果几乎总是「把僵尸调强」。

**⚠️ 这是一个条件 story。** 默认**不排入 `[SP]` 计划**，仅当 Story 3.7 或 3.1 的试玩
观察到触发条件时才开启。开启条件见下。**它在 `[SP]` 时须被显式标为 deferred，
而不是遗漏 —— 遗漏会让 GDD 承诺的处置路径悄悄消失。**

> 设立原因：GDD「Difficulty and Replayability」承诺「若孩子出现战斗疲劳则重新评估」，
> 但 `[CE]` 同时把战斗层难度变化列为 OUT-OF-SCOPE-4 / Epic 3 范围外
> —— 承诺与范围外相互矛盾，等于**没有路径**。本 story 是那条路径。
> 详见 `[IR]` 报告 HIGH-2。

**Acceptance Criteria:**

**Given** Story 3.1 的试玩走查中出现战斗层疲劳迹象
**When** 判定触发条件
**Then** 触发条件 = 以下任一：
      ① **太难** —— 反复重打、主动要求退出、看到僵尸出现紧张/回避行为
      ② **太重复** —— 打得轻松但不想玩，主动询问「还有吗」后走神或要求换游戏
**And** 判定结论须**写入 Story 3.1 的问题清单**，附孩子的原话或可观察行为
**And** 「太难」与「太重复」须分别判定 —— 二者处置方向相反，不可合并处理

**Given** 判定为「太难」
**When** 处置
**Then** 数值**下调**：僵尸血量 / 移动速度 / 每回合数量，三者中至少一项降低
**And** **不新增玩法、不改塔型、不改路径结构** —— 结构不变是 v1.0 的不做项（OUT-OF-SCOPE-4）
**And** 改后重跑 `npm run balance-sim`，并按 Story 3.6 走断言更新流程

**Given** 判定为「太重复」
**When** 处置
**Then** 只动**节奏与表现层**：出场节奏、单局回合数、反馈即时感
**And** **战斗数值一律不动** —— 若本判定下数值发生了变化，说明判定做错了，回到判定环节
**And** 单局回合数的改动须回写 GDD「Progression and Balance」中「一局 ≈ 10 题」一条

**Given** 两个方向都验证过仍无改善
**When** 升级决策
**Then** 上调僵尸强度 / 扩展路径复杂度是**最后手段**，且属于范围变更 ——
      须先改 GDD 与本文件的 OUT-OF-SCOPE-4，再动手，**不得先改实现**
**And** 该情形须向家长说明并取得确认（用户的判断优先于 `[IR]` 的建议）

**📎 覆盖：** FR34–FR41、FR51（GDD「战斗层全程一致」的例外处置路径）；条件触发，**不计入 Epic 3 的常规 story 数**
