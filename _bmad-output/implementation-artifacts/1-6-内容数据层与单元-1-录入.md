## Story

As a 家长,
I want 教材内容能像填表格一样录进去、录错了当场被抓出来,
So that 我不需要写代码就能往游戏里加孩子要学的内容。

**这个 story 是整个项目「内容量」的第一次真实落地。** 旧版本历经 5 个大版本、
`public/assets/` 仍只有 9 张图，最终被家长以「没有学习内容」否决。本 story 是那道生死线
（Story 1.19）的输入端。

## Acceptance Criteria

### AC 组 1 —— Zod schema（`src/content/schema.ts`）

**AC-1** `src/content/schema.ts` 用 **Zod 4**（已装 `4.6.6`，见「技术要点」）定义 schema，
覆盖且仅覆盖这些导出：`UnitSchema` / `CardSchema` / `OptionSchema` / `TowerBindingSchema`
（命名可调，但**四个概念必须各有对应导出**）。

**AC-2** `Card.kind` 三态 `word` / `keyword` / `response`；`Option` 两态 `ImageOption` / `TextOption`。

**AC-3** 🔥 **「唯一正确项」是 schema 级约束**：每张卡的 `options` 中
**恰有且仅有 1 个** `correct: true`。
- 0 个 → 必须报错（「本题没有正确项」）
- 2 个及以上 → 必须报错（「本题有多个正确项」）
- 这是 **FR16**，由架构模式 B 明文指定为 Zod 职责（`game-architecture.md:869`）。

**AC-4** **卡面 TTS 文本不得为空** —— `promptText` 经 `trim()` 后长度 ≥ 1。
纯空白串同样算空。

**AC-5** 🔥 **卡型与选项形态相符**（AC 组 2 第 4 类错误的 schema 部分）：
- `kind === 'word'` → **全部**选项必须是 `ImageOption`（有 `imageSrc`，无 `text`）
- `kind === 'keyword'` / `'response'` → **全部**选项必须是 `TextOption`（有 `text`，无 `imageSrc`）

> **这条为什么落在你身上：** `src/core/types.ts:216` 把架构模式 B 的三分支并集**拍平**成了
> `{ kind: CardKind; options: readonly Option[] }`，因此 `{kind:'word', options:[{text:'…'}]}`
> 在 `core/` 里能**干净编译**，且 `core/` 内没有任何运行时守卫拦它。
> `deferred-work.md` 已把它正式移交给你：
> > 「已登记为 deviation，由 Story 1.6 的 Zod schema 兜底。恢复条件：Story 1.6 录入内容时，
> > 把「`kind: 'word'` 的 options 必须是图片」写成 Zod 断言，并给 `src/content/` 的坏数据补一条测试。」

**AC-6** **选项不得混入其他单元的词条** —— 每张卡每个选项的 `id` 必须与所属 `unit` 的单元号
一致（`u1-` 开头），详见「内容模型裁决」第 3 条。

**AC-7** **塔绑定指向不存在的塔型** —— `TowerBinding.towerType ∈ {'direct','slow','aoe'}`。

**AC-8** **`entryId` 全局唯一**，且必须匹配 `/^u\d+-[a-z0-9]+(?:-[a-z0-9]+)*$/`
（kebab-case + 单元前缀，AR29）。**「文件存在 ≠ 正确」**：`u1-dog-`（尾部连字符）
与 `u1-Dog`（大写）都必须被抓出。

**AC-9** schema 导出的 TS 类型必须与 `src/core/types.ts` 的既有类型**对齐**：
`Card` / `Option` / `ImageOption` / `TextOption` / `DeckEntry` / `TowerType` 六个名字
在内容层导出后，`createInitialState({ unitNumber, deck })` 必须能直接吃
`content` 导出的 deck（**不经过任何手写转换函数**）。见「内容模型裁决」第 1 条。

### AC 组 2 —— 校验脚本（`scripts/validate-content.ts`）

**AC-10** `npm run validate:content` 在内容有错时**退出码非 0**。
当前实现恒 `exit 0`，`scripts/validate-content.ts:14-15` 明写
「『跑过了 validate:content』这句话在此之前不构成任何证据」。本 AC 就是来消灭这句话的。

**AC-11** 🔥 **五类错误逐条抓出，且报错可定位到具体词条 id**：

| # | 错误类别 | 落点 | 报错必须能定位到 |
|---|---|---|---|
| 1 | 词图文件缺失或命名不符 | **脚本**（需 `node:fs`） | 词条 id + 期望路径 + 实际找到的文件 |
| 2 | 塔绑定指向不存在的塔型 | **Zod** | 词条 id + 收到的非法值 |
| 3 | 选项中混入其他单元的词条 | **Zod** | 卡 id + 具体选项 id + 所属单元号 |
| 4 | 卡型与选项形态不符 | **Zod** | 卡 id + 卡型 + 具体选项 id + 实际形态 |
| 5 | 卡面 TTS 文本为空 | **Zod** | 卡 id + `promptText` 所在路径 |

**AC-12** 校验必须**覆盖全部单元文件**，不是只校验单元 1。
新增 `unit-NN.json` 无需改脚本即可被校验（AC-6 需要跨单元比对，因此校验器必须加载全部单元）。

**AC-13** 日志前缀 `[content]`，错误走 `ERROR` 级（架构 `:609`、`:615`）。
`docs/**` 之外的输出格式自定，但**错误行必须逐条独立可读** —— 不得把 30 个错误压成一行。

**AC-14** 校验通过时输出明确的通过信息与统计（单元数 / 卡数 / 三型分布），
并**退出码 0**。

**AC-14.1** 🧪 **校验逻辑必须可测 —— 纯逻辑与副作用分离**：
校验的**主体**（加载单元 → 跑 Zod → 查词图 → 汇总问题）导出一个**纯函数**，
返回结构化的结果对象（`{ ok: boolean; problems: Problem[]; stats: Stats }`）；
`console.log` / `process.exit` 只允许出现在最外层的 `main()` 里。
- **这是 Story 1.3 已确立的模式**：`scripts/generate-voice.ts` 的「纯逻辑导出可测、
  副作用集中在 `main()`」，`tests/scripts/generate-voice.test.ts` 67 条用例正是这么测的。
- **理由**：若校验逻辑全部埋在 CLI 里，测试就只能 `spawn` 子进程断言退出码 ——
  而 1.5 的 `[CR]` 抓到过「断言退出码抓不到差异」的假绿
  （`1-3`：`--only --dry` 首版用例退出码同样是 1，只是变成「没有匹配到任何词条」）。
  结构化结果才能断言「报的是哪一类错误、定位到哪个词条」。
- 词图路径解析**参数化**（传入根目录），让测试能用临时目录喂假文件系统，
  不要在纯函数里硬编码 `public/assets/words/`。

> ⚠️ 用子编号 `AC-14.1` 而非插入新号，是为了不打乱后续 AC 的编号 ——
> Dev Agent Record 的自查表与 Completion Notes 都按 AC 号引用。

### AC 组 3 —— 单元 1 真实内容（`src/content/units/unit-01.json`）

**AC-15** 🔥 **`entryId` 集合必须与 `public/assets/audio/voice/` 下已存在的 38 个 mp3 完全一致**
（一不多一不少）。**已实测确认**：`2026-10-14` 比对 `scripts/data/voice-entries.json` 的 38 条
与 `audio/voice/` 的 38 个 mp3，**两侧集合完全相同**（30 词 + 8 句，id 全带 `u1-` 前缀）——
注意词表文件本身**不是按字典序排的**，比对时必须两侧都 `sort`，否则 `diff` 会报出
`u1-sister` / `u1-student` 的假差异。理由与核查命令见「不可逆约束」一节。

**AC-16** 单元 1 全部词汇（30 词）与句子（8 句）均已录入。

**AC-17** **单词卡、关键词卡、回应卡各至少一道**（FR19）——
实际交付远超「至少一道」，三型都要成规模（见「内容模型裁决」第 5 条）。

**AC-18** 短语（如 `good morning`）**作为回应卡的正确回应出现，不单独成卡**。
即：不存在 `promptText === 'good morning'` 的独立短语卡；它作为某张回应卡的**选项**。

**AC-19** `npm run validate:content` 通过；**人为注入 AC-11 五类错误中的任一类时能抓出**
（逐类验证，见 Tasks Task 6）。

**AC-20** 单元 1 的三型卡数、词条数**写入 `docs/art-direction.md` 或 story 的 Completion Notes**，
作为 Story 2.1 计算「需配图词条实际占比」的输入（GDD `:605-608` 自认 200-400 张的估算
基于未经核实的 100% 配图假设，`[IR]` MEDIUM-7）。

### AC 组 4 —— 词图规格与色板定稿（`docs/art-direction.md`）

**AC-22** **词图规格必须定稿**以下全部项（架构 `:370-377` 只锁了前三项，后两项是「Epic 1 定稿」
即本 story 的活）：

| 项 | 值 |
|---|---|
| 格式 | **SVG**（架构已锁） |
| 画布 | **正方形**（架构已锁） |
| `viewBox` | **统一数值** —— ⚠️ 架构未给数值，**由本 story 定**（建议 `0 0 512 512`） |

| 路径 | `public/assets/words/unit-01/<entryId>.svg` |
| **具体尺寸** | ⚠️ **由本 story 定**（建议 512×512，必须与 `viewBox` 一致） |

  `--color-bg` / `--color-path` / `--color-tower-shooter` / `--color-tower-slow` / `--color-tower-aoe`
  / `--color-zombie` / `--color-sun` / `--color-heart` / `--color-correct` / `--color-wrong`
  / `--color-overlay-range`
- ⚠️ **`--color-tower-slow` 与 `--color-tower-aoe` 必须给出可区分于 `--color-tower-shooter` 的色值** ——
  Story 1.7 AC：「三种塔型在视觉上**必须可区分** —— 孩子要能看出哪株是减速塔、哪株是范围塔」。

### 二、内容模型裁决（架构未定义，本 story 自定 —— 请照此实现并申报）

架构文档**从未定义过 `Unit` 与 `TowerBinding` 的字段集**（这两���类型名只出现在 Story 1.6 的 AC 里）。
以下 5 条是本 story 的裁决，实现时照做，并在 Dev Agent Record 里逐条申报偏离。

**1. 单元 JSON 的条目形状 === `DeckEntry`，不另起炉灶**

`src/core/types.ts:246-253` 已定义：
```ts
interface DeckEntry {
  readonly entryId: string
  readonly wordId: string
  readonly towerType: TowerType
  readonly card: Card
}
```
`createInitialState({ unitNumber, deck })` 直接吃 `readonly DeckEntry[]`。
⇒ **schema 的导出类型必须能直接喂给它，中间不得有手写转换函数。**
`TowerBinding` 定义为 `DeckEntry` 里 `{ wordId, towerType }` 那部分（给它一个名字，不重复结构）。

**2. `entryId` 与 `wordId` 都带单元前缀，取值策略**

- `entryId`：内容条目的唯一 id，`u1-dog`、`u1-s-how-are-you`
- `wordId`：塔的显示名来源 —— **本 story 定为与 `entryId` 同值**。
  架构 `:875-880` 只说「`wordId` 是显示名/词图来源」，没说它必须与 entryId 不同。
  同值的理由：塔图按**塔型**做、不按词做（Story 1.7），`wordId` 在本阶段唯一的实际用途
  就是显示单词本身；引入两个 id 只会多一处可能不一致的地方。
  ⚠️ 若你决定分开，必须补一条测试锁住两者的映射关系。

**3. 🔥 选项的 `id` === 词条 id**

```
ImageOption.id = 'u1-dog'          // ← 词条 id，不是 'u1-dog-o1'
TextOption.id  = 'u1-s-i-am-fine'  // ← 同理
```
这一条解决三件事，且是 AC-11 第 3 类错误能落地的前提：
- 「选项中混入其他单元的词条」→ 检查 `option.id` 的 `u<N>-` 前缀 vs `unit` 编号，**判据唯一**
- 选项朗读走录音主通路 → `playPronunciation(option.text, option.id)`，
  架构 `:381` 规定录音文件名 = 词条 id，而 `audio/voice/` **不按单元分层**，
  选项 id 若不是词条 id 就**没有录音**，朗读会静默降级到设备 TTS
- 选项 id 全局唯一 ⇒ 天然防重复

⚠️ 这与 `tests/fixtures/synthetic-deck.ts` 里的 `${entryId}-o1` 形态**不同** ——
那是测试 fixture，**有意保持不变**（其文件头第 1 条：「为什么不用 `src/content/` 的真实内容？
用真实内容会让回合层测试随内容录入而变红 —— 那是另一条轴的失败」）。**不要去"统一"它们。**

**4. 不建 `loader.ts`**

架构目录树 `:725` 有 `content/loader.ts「按单元加载」`，而决策 3 的存储位置块 `:288-302` 没有它。
架构 `:900` 同时定案「JSON 模块直接 `import`（Vite 处理），启动时 Zod 校验」，
**无远程、无运行时拉取** ⇒ 「按单元加载」就是 `import unit01 from './units/unit-01.json'`，
这活儿本来就在 `index.ts` 里。**不建 `loader.ts`**，作为 deviation 申报。

**5. 三型卡的分配**

以 38 条词表（30 词 + 8 句）为全集：
- **单词卡**：题面 = 30 个单词之一；4 个选项全为 `ImageOption`，
  id 取自**其余单词**的词条 id（含其他词条作为干扰项）
- **关键词卡**：题面 = 8 个句子之一；选项全为 `TextOption`，正确项 = **句中出现的那个词**

### 五、技术要点

**Zod 4，不是 Zod 3** ⚠️

仓库装的是 `zod@4.6.6`，但网上绝大多数 Zod 教程是 v3。**从 v3 抄来的写法会在 v4 报错**：

| 事项 | v4 事实 |
|---|---|
| 报错列表 | `result.error.issues`（**`.errors` 与 `.formErrors` 已移除**） |
| 报错格式化 | `z.prettifyError()` / `z.treeifyError()` / `z.flattenError()` |
| `.superRefine()` | 2025-08 起**重新启用**（曾短暂废弃改叫 `.check()`），**两者都可用** |
| `ctx.addIssue()` | 仍可用；`message:` 键正在迁往 `error:` |
| `z.discriminatedUnion()` | **API 未变**，但不能像旧的 `ZodEffects` 那样被包一层 |
| 类型谓词收窄 | **v4 不再收窄** —— `.refine((v): v is string => ...)` 推导出的是 `unknown` |

> ⚠️ **`OptionSchema` 的两态推荐用 `z.discriminatedUnion`**，判别键用
> `kind: 'image' | 'text'`。但若你不加 `kind` 字段（core 的 `ImageOption` / `TextOption`
> **没有** `kind` 字段），改用 `z.union` + 形状差异即可。

**⚠️「只 throw，不静默兜底」**

架构 `:566-571` 的分层错误策略：**纯逻辑层必须 `throw`，禁止 catch**。
`z.safeParse` 失败后若你写 `?? 默认值` 继续跑，`validate-content.ts` 就重演
「恒定退出 0」的假绿 —— 那是本 story 要消灭的东西本身。

**塔型单一事实源** ⚠️

架构无明确规定，但 `TOWER_TYPES` 已在 `src/core/balance.ts` 导出并 `Object.freeze`，
`assertTowerType()` 也在运行期校验。
⇒ **不要在 `content/schema.ts` 里另写一份 `z.enum(['direct','slow','aoe'])`
就当它是对的**。正确做法：用 `z.enum` 声明，同时**加一条测试**断言
内容层的塔型集合 **=== `TOWER_TYPES`**。

**ESLint 相对路径形态**

项目**没有 `@/` 别名**（tsconfig 无 `paths`、vite 无 `resolve.alias`）。
`eslint.config.js` 的 `no-restricted-imports` 注释写着：

⇒ 你的 import 一律用 `../core`、`./units/unit-01.json` 这种相对形态。

⇒ 内容层测试只用纯函数与 `node:fs`，**不要碰组件**。
