# Story 1.20: 相邻不同型 —— 把「植物不重复」从巧合变成代码保证

## Story

As a 4–8 岁的孩子,
I want 每次答对单词时看到的植物**和上一次不一样**,
so that 一局打完不觉得「一直见同一株」。

## ⚡ 给 Dev 的 60 秒速读（**先读这段，再读别的**）

1. **本 story 一行塔型都不改**：`towers/` 仍恰好 3 个 svg，不按 `wordId` 出图，不做图鉴。只改**发牌顺序**。
2. 🔥 **单元 1 今天已经满足规则**（全 37 条相邻重复 = 0），但那是手写 JSON 的巧合，代码零保证。
   **所以你写的重排对单元 1 必须是恒等变换** —— 这是保住 10+ 条现有测试的唯一办法。
3. 🔥 **三条「不许」比实现本身重要**，见下方「🚨 本 story 的高危点」。写完自查那三条。
4. **起号**：守卫从 **G173**、变异从 **M192**（已 grep 实测：全仓最大 G172 / M191）。

## §0 裁决 —— 已定，Dev 不必重新决定

### 裁决 1 —— 🔥 需求必须窄化，这是它能落地的前提

用户需求逐字：「答对单词后，出现新的植物，如果之前这个植物已经出现了，不用重复出现」。

按字面理解（「一局 10 题用掉 10 个不同植物」）**物理无解**：`towers/` 下**恰好 3 个** svg
（`direct` / `slow` / `aoe`），`QUESTIONS_PER_LEVEL = 10` ⇒ 鸽笼，每局至少 7 次重复。
**任何塔型配比平衡都救不了**（单元 1 的塔型在 JSON 序上本就是近乎完美的 round-robin，
最好的局与最坏的局只差 1）。

**本 story 采用的窄化口径：「同一局里相邻两题的塔型不同。」**
这是一条**排序约束**而非**配额约束** —— 配额约束在 3 型下无解，排序约束恒可解。
**两者的区别就是裁决必须落窄的原因，不是措辞让步。**

> ⚠️ **代价必须逐字记住**：同一局内**仍必有约 3 次重复**。
> 本 story 兑现的是「看起来在换植物」，**不是**「每题都是新植物」。
> 注释、文档、对外说明**一律不得写成后者**。

### 裁决 2 —— 绕开的三条拦截，本 story 一条都不碰

| FR70「美术资产按塔型制作（2-3 套），不按词制作」 | **不动**（不按 `wordId` 出图） |

⇒ 因为只改顺序、**不改「塔型 ↔ 词」的绑定关系**，本 story 不与任何已交付决策冲突。

### 裁决 3 —— 🔥 为什么单元 1 已经满足，而本 story 仍要做

实测 `src/content/units/unit-01.json` 全部 37 条：**相邻重复 = 0 处**，塔型分布
`{direct: 13, slow: 13, aoe: 11}`。前 10 条切片 = `direct slow aoe direct slow aoe direct slow aoe`。

但 `src/core/deck-slice.ts` 是 `filter` + `slice` 的**三行纯函数，完全不看 `towerType`** ⇒
**今天满足纯属手写 JSON 的巧合**。Epic 2 要手工录入 13 个新单元，没有人保证它们也恰好排成这样。

**本 story 的价值不在单元 1，在 Epic 2。**

## 🚨 本 story 的高危点（事故卡）

1. 🔥 **把「相邻不同型」实现成洗牌** —— 直接违反 A4 / AR6，且会让同一次存档恢复
   在不同机器上得到不同题单。**确定性是第一要求，不是性能。**

2. 🔥 **实现得「太聪明」，顺手把原序也改了** —— 单元 1 本来就合规，
   任何非恒等的重排都会打红 `store-deck-slice.test.ts:92`。
   **看到那条测试红了，先怀疑自己，不要改测试。**

3. 🔥 **全同型输入抛错 / 死循环** —— 34 条现有夹具全是 `'direct'`。
   A3 的降级路径是它们唯一的活路，**不是可选的优雅性**。

4. 🔥 **又写一条源码扫描守卫** —— 「不许写死塔型」这类判据有过等比缩放逃逸的实测记录（M172′）。
   本 story 的守卫必须**真的去跑**。

5. **新建一个 `src/core/deck-order.ts`** —— 看着更干净，但 G161 的调用点集合
   与 `looksLikeCopiedJudgement` 都对新增文件敏感。**留在 `deck-slice.ts` 里。**

6. **改 `towers/` 或单元 JSON** —— 一行都不该动（裁决 2）。

7. ⚠️ **把「看起来在换植物」写成「每题都是新植物」** —— 数学上就是错的，
   且 3 型 × 10 题决定了它永远错。见裁决 1。

## Dev Notes

### 现有代码逐字速查（Dev **必读**，不要凭记忆）

`src/core/deck-slice.ts` 全文 **75 行**，核心三行：
```ts
export function sliceDeckForLevel(
  entries: readonly DeckEntry[],
  masteredWordIds: readonly string[],
): DeckEntry[] {
  const mastered = new Set(masteredWordIds)
  const pending = entries.filter((entry) => !mastered.has(entry.entryId))
  return pending.slice(0, QUESTIONS_PER_LEVEL      // ← B1：这一行逐字不动
}
```
- `filter` **保序** ⇒ `pending` 就是单元 JSON 原序；`slice` 取前 10。**没有任何 towerType 逻辑。**
- 文件头逐字硬约束（第 11 行）：「**纯函数**：零 DOM、零 Vue、**零随机**、零时间」
- 文件头第 16-17 行逐字：「**本模块是切片判据的唯一定义处**（R-02 / AC-F5 第二条）：
  `app/` 与组件层调它，不允许出现第二份实现。」
- `QUESTIONS_PER_LEVEL = 10` 在第 44 行，**全仓唯一出处**，G160 逐字扫 `src/` 防字面量 `10`

### 下游怎么消费（**实测：全库零位置依赖**）

- `nextQuestion()`（`reducer.ts:172-183`）**线性扫 `deck`** 取第一个未掌握未跳过的
  ⇒ **deck 的数组顺序就是出题顺序**，这是唯一的功能耦合。
- **全库没有 `deck[0]` 依赖**（`src/` 里一处也没有；`balance-sim.ts:478` 那个在它自己的合成题单上）
- 查找一律按 `entryId`：`requireEntry`、`build.ts:128/235` 都是 `deck.find(...)`
- `assertDeckRelations` 是**集合式、对顺序免疫**（`new Set(state.deck.map(e => e.entryId))`）
- 手牌顺序来自 `state.unlocked`（= 答对顺序），**与 deck 顺序无关**（`build.ts:218-222` 逐字）
- ⇒ **重排不会撞任何不变量**，但会改变「哪题在第几个回合」⇒ 可能改变战斗结果
  （⚠️ `tests/app/level-flow.test.ts:452-472` 走真实 store，**行为敏感，须实跑不可推定**）
