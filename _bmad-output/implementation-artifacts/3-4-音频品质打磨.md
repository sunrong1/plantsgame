## Story

As a 孩子,
I want 念出来的声音跟课本录音听起来像、音效也更好听,
So that 我听到的就是我在课本上听到的那个声音。

**依赖：** Epic 1 的音频链路（Story 1.2 / 1.3 / 1.14）+ Epic 2 的单元 2 录音（Story 2.5）。
**不依赖** 3.1 的试玩清单（那三个 story 要的是「全部单元 + 真实试玩数据」，今天都不成立）。

## Acceptance Criteria

### AC-1 「只改品质，不改职责」（epics 逐字）

**Given** Epic 1 已跑通音频链路与因果正确性
**When** 打磨品质
**Then** **只改品质，不改职责** —— 音效的职责仍是「帮助孩子理解刚才发生了什么」，
      不新增装饰性音效

### AC-2 朗读主通路的参数边界（epics 逐字）

**Given** 朗读主通路为预生成录音（架构决策 7，2026-10-12 纠偏后）
**When** 打磨品质
**Then** **音色本身已定**（`English_LovelyGirl`，英式女童声），**不再变更**
      —— 变更音色意味着全书单词词（教材词表全量）全部重生成
**And** 只调**录音生成参数**（语速 / 音高），并重新生成受影响的词
**And** 校准的判断标准仍是**孩子听长句时能稳定提取关键词**
**And** 若发音清晰度不达标（孩子提取不出关键词），调生成参数**重生成**，
      而非切回设备 TTS —— 设备 TTS 仅是录音缺失时的兜底，不是品质选项
**And** 设备 TTS 的音色不参与品质决策（它只在录音缺失时才可能被听到）
**And** 走既有的统一 `playPronunciation(text, entryId?)` 接口，不新增分支逻辑

> 📎 **AC-2 与架构决策 7 的关系**（不冲突，但要读懂）：
> 架构「两条不可协商的生成约束」第 1 条逐字是「**一次性全量生成，mp3 提交进 git，永不重新生成。**」
> 它的理由逐字是「TTS API 无 `seed` / `temperature` 参数，不保证跨批次音色一致」。
> ⇒ **约束的对象是「分批混录」**，不是「重生成」：同一份产物里混着两组参数 = 音色可能不一致；
> 而**用同一组参数整批重录**正是这条约束允许的形态（它自己接着写「变更音色 = 全书单词词全部重生成」）。
> ⇒ 本 story 的重生成**只允许整批**（见 AC-7），零散补录一律禁止。

### AC-6 录音生成参数必须**可审计**（本 story 新增）

> **为什么 epics 没写但本 story 必须有**：AC-2 允许改「语速 / 音高」并重生成。
> 但仓库里**没有任何东西守得住「改了参数却没重生成」**——
> `scripts/generate-voice.ts` 的指纹闸只在**运行脚本那一刻**生效（退出码 1），
> 而**已提交进 git 的那 75 条 mp3 与已提交的 `manifest.json` 没有任何守卫**。
> ⇒ 提交态可以自相矛盾（`VOICE_SPEED` 是 0.95、manifest 写着 0.9、录音还是 0.9 录的），
> 而**没有任何测试会红**。本条把「常量 / 请求体 / 指纹 / 已提交 manifest」四者绑成一条链。
>
> ⚠️ **还有两处同类隐患在本条之外**（本 story 顺手记一笔，见 §6 裁决 E）：
> ① 指纹**只在 `manifest` 存在时**才生效 ⇒ 「只删 manifest、不删 mp3」会绕过整道闸（AC-7 展开）；
> ② `SAMPLE_RATE` / `BITRATE` / `CHANNEL` 三个**同样决定音频内容**的常量**不在指纹里**
> （`VoiceFingerprint` 只有 model / voice_id / speed / format 四个字段）—— 变了也不会触发拒跑。

**Given** 脚本的录音生成参数（模型 / 音色 / 语速 / 音高 / 格式）
**When** 有人改了其中任何一个
**Then** 该参数必须同时出现在三处：① 请求体 `voice_setting` ② 溯源指纹 `VoiceFingerprint`
      ③ `scripts/generate-voice.ts` 的常量区
**And** **已提交的** `public/assets/audio/voice/manifest.json` 的指纹必须与当前常量**一致**
      —— 不一致即报红（**守卫 G310**）
**And** 指纹比较必须把「manifest 里没有这个键」归一为该参数的**历史默认值**，
      不得归一为**当前常量值**（理由见 §3.1 —— 归一方向搞反会把违规放过）
**And** 指纹比较必须**逐键**做，**不许**用 `JSON.stringify` 比整份对象
      —— 归一后的键序与 `currentFingerprint()` 的键序**必然不同**（`pitch` 会被排到最前），
      整对象序列化比较会把「现状」误判为不匹配（§3.1）
**And** 归一后 manifest 的**键集合**必须与 `currentFingerprint()` 的键集合**恰好相等**
      —— manifest 里**多出来的键**也要报（只比「当前常量有的那几个键」会把多出来的键放过）

### AC-7 改参数 ⇒ 必须整批重生成，不得零散补录（本 story 新增）

> **为什么 epics 没写但本 story 必须有**：AC-2 说「重新生成受影响的词」，
> 而脚本的指纹闸**只在 `manifest` 存在时生效** —— `manifest === null` 时只打一条 INFO 就继续跑。
> 此时 `decideSkip` 的 `unrecorded` 分支会把磁盘上**已有的旧录音登记进新 manifest**（新指纹）
> ⇒ **只删 manifest、不删 mp3** 就会得到一份「混批却被祝福」的产物
> （旧的旧参数音频 + 新的新参数指纹），**G310 也抓不到**（manifest 与常量一致得很）。
> ⇒ 必须把「整批」这条变成**机器可判定**的，而不是靠人记得。
>
> 📎 **今天 `--only` 反而造不出混批**（复核实测，别把它当成漏洞）：
> `--only` 的过滤发生在**指纹闸之前**，而闸又在 `runBatch` 之前 ⇒ 改了参数就会先被闸拒跑，
> 压根走不到生成。⇒ 真正的漏洞是上面那条**「只删 manifest」**。

**Given** 磁盘上的录音与当前常量不同源（指纹不匹配）
**When** 运行生成脚本
**Then** 脚本必须**拒绝运行**（退出码 1）并**指名差异**（哪个键、从什么变成什么）
      —— 不得静默重生成、不得零散补录
**And** 该拒绝行为必须有守卫钉住（**守卫 G311**），且守卫必须真的调得到那条路径
      （⚠️ 现在 `main()` 读的是模块级常量路径，测试改不动 ⇒ 见 Task 3 的小重构）
**And** 改参数后的正确流程是「**整批**重来」，且该流程必须可用（`--help` 写清楚）
**And** ⇒ 正确流程逐字是「**删整个 `public/assets/audio/voice/` 目录**（mp3 与 manifest 一起删）再重跑全量」**

**Given** 磁盘上已有 mp3，但**没有 manifest**（或 manifest 被手工删了）
**When** 运行生成脚本
**Then** ⚠️ **「只删 manifest、不删 mp3」这条路径必须被显式堵住** ——
      要么脚本在「没有 manifest 但磁盘上已有 mp3」时**拒绝运行**并要求整批重来，
      要么它**不把旧 mp3 登记进新 manifest**（`decideSkip` 的 `unrecorded` 分支今天会登记）
**And** 二选一**必须选一条并写进注释** —— 不许留给下一个人猜
      （今天的行为是「跳过旧 mp3 + 登记进新 manifest」⇒ 旧参数音频被盖上新参数的戳）

并把**已经存在但没人守**的那个洞（改了参数不重生成 ⇒ 提交物自相矛盾）钉死。
**不做**：任何**参数取值**的改动（人的裁决）、任何**辅通路**的改动、
任何**音效/BGM 资产**的改动、任何**音效语义**的改动。

### 3. 三个最容易做错的技术点

#### 3.1 指纹归一化的**方向**与**比较方式**（AC-6 / Task 1.4）

加了 `pitch` 键之后，已提交的 manifest 里**没有**这个键（它是历史产物）。
于是「缺键」必须被解释成什么？

- ❌ **归一为当前常量值**：`{...cur, ...manifest}` ⇒ manifest 缺 `pitch`、当前 `VOICE_PITCH = 2`
  ⇒ 归一后 manifest 的 `pitch` 也变成 2 ⇒ **判为匹配** ⇒ 「改了音高却没重生成」被放过。
- ✅ **归一为历史默认值**：`{...HISTORICAL_DEFAULTS, ...manifest}`，`HISTORICAL_DEFAULTS = { pitch: 0 }`
  ⇒ manifest 缺 `pitch` ⇒ 记 0；当前常量 0 ⇒ 匹配（现状仍然有效，**75 条录音不必重生成**）；
  当前常量改成 2 ⇒ 不匹配 ⇒ 脚本拒跑 + G310 报红。

⇒ **归一必须用「历史默认」，不是「当前常量」。** 这一条写反了，AC-6 就整个失效。

⚠️ **`HISTORICAL_DEFAULTS` 只能含 `pitch: 0`** ——
`model` / `voice_id` / `speed` / `format` 四个键在已提交 manifest 里**一直都在**，
它们「缺键」本身就是异常；把任何一个放进默认表 = 把异常归一成正常。

⚠️ **比较方式必须同时改成逐键**（这一条比方向更容易被漏）：

现在的 `fingerprintMatches` 是 `JSON.stringify(m.fingerprint) === JSON.stringify(currentFingerprint())`
—— **键序敏感**。而归一化用的 `{...HISTORICAL_DEFAULTS, ...manifest.fingerprint}` 会把 `pitch`
排到**最前**，`currentFingerprint()` 里它排在**最后** ⇒ 两个 `JSON.stringify` **必然不等**
⇒ 现状（`VOICE_PITCH = 0`）会被误判为不匹配（G310 红 + 脚本拒跑）——
**正是「75 条录音不必重生成」这条承诺的破口**。
⇒ 实现者极可能去「修归一化」而不是「修比较方式」，从而写出 `{...cur, ...manifest}` 那种把违规放过的写法。
⇒ **判据里不许出现 `JSON.stringify`**：逐键 `===`，并额外断言 manifest 的键集合**恰好等于**
`currentFingerprint()` 的键集合（**多出来的键也要报**）。
（与 R-51「断言必须真能咬住它要防的违规」同源：判据的默认值方向就是它的牙齿。）

#### 3.2 「整批」不是「重新生成受影响的词」

⚠️ **先纠正一个容易想当然的说法**：今天 `--only <前缀>` **造不出混批** ——
`--only` 的过滤在**指纹闸之前**，闸又在 `runBatch` 之前 ⇒ 改了参数就会先被闸拒跑，压根走不到生成。

**真正的漏洞是「只删 manifest、不删 mp3」**：闸**只在 `manifest` 存在时**生效
（`manifest === null` ⇒ 只打一条 INFO 就继续）⇒ 此时 `decideSkip` 的 `unrecorded` 分支
会把磁盘上**已有的旧录音登记进新 manifest**（新指纹）⇒ 旧的旧参数音频被盖上新参数的戳，
而 G310 **抓不到**（manifest 与常量一致得很）。

⇒ 正确流程：**改常量 → 指纹不匹配 → 脚本拒跑 → 删整个 `public/assets/audio/voice/` 目录
（mp3 与 manifest 一起删！）→ 重跑全量 → 新的 manifest 记录新指纹**。
⚠️ 只删 manifest 那一半，就是上面那条漏洞。
⇒ `--force` 能不能越过指纹闸是**待裁决项**（§6 裁决 F / Task 4.2）——
   闸不可绕 ⇒ 改了参数后仍须手工 `rm`，而那正是 DF-010 的痛点。

#### 3.3 判据里不许出现第二份数值

仓库里已有第二份数值：`tests/scripts/generate-voice.test.ts` 的「请求体带上音色、模型与语速」
逐字断言 `body.voice_setting.speed).toBe(0.9)` —— 那是**金标准**（改常量时它会红，逼人 conscious 地更新），
不是「第二份事实源」（后者会悄悄漂移）。
⇒ 新增 `pitch` 断言时沿用同一形态，并额外保证**请求体 / 指纹 / manifest 三处同源**
（都取自脚本常量，不各自写死）。
