## §1 目标与不变量

### 目标

1. **活跃区里只剩真正还活着的内容** —— 已结条目移进归档（默认不读）。
2. **活账本能被一眼扫完** —— 每条一行，不再有段落级的论证堆在账本里。
3. **「哪些还开着」不再需要通读全文才能回答** —— 状态字段化。
4. **原文一条不丢、且只有一份** —— 搬迁是「移动」，不是「复制」（R-37 的复制链坑）。

### 不变量（本次不得违反）

| 不变量 | 依据 |
|---|---|
| 数值一个字不改 | R-20 |
| `src/` `tests/` 的**行为**不改（只改注释与引用文字） | 本次是文档治理 |
| 任何原文不得被「顺手改写」 | R-31 / R-57 |
| 引用用**原句**或稳定 ID，不引行号 | R-31 |
| 已结 story 文档移入 `archive/` 是**收尾动作的一部分**，不另开归档 | R-40 |

## §2 目标形态：三层

| 层 | 位置 | 内容 | 体量 | 默认检索可见 |
|---|---|---|---|---|
| **活账本** | `implementation-artifacts/deferred-work.md` | **只列仍开放的条目**，每条一行表格行 | 数十行（**待 §4 枚举后校准**） | 是 |
| **详情** | `implementation-artifacts/deferred-details.md` | 开放条目的完整论证（按 DF-ID 分节） | ~20–40KB | 是 |
| **历史** | `_bmad-output/archive/deferred/` | 已结 / 作废条目的完整原文 + 分诊结论 | ~250KB | **否** |

**为什么详情留在活跃区**：已结条目的论证可以进归档（它已落成代码或已被裁决）；
但**还开着的**条目的论证若也进归档，等于让活问题只剩一行摘要 —— 考古成本高，
且 R-40 的理由（「已完成 = 已落成代码与测试」，故默认不读）对它们**不成立**。
留在活跃区意味着这些是**真活的内容**，值得被 grep 到。

**文件名 `deferred-work.md` 不改**：R-35 规则正文、`docs/` 多处、`sprint-status.yaml`
的指针都指着它，改名的连带面远大于收益。

## §3 ID 与命名

### DF-ID

- 活跃条目一律 `DF-001`、`DF-002`……**单调递增、永不复用**，活账本按 ID 排。
- **只有开放条目分配 DF-ID**。已结 / 作废条目保留**旧编号**作为历史标识
  （`E1`–`E42` / `W1`–`W9` / `D1`–`D7` / 裸数字 `1`–`45`）。
- 归档目录 README 出对照表：`旧编号 → DF-ID → 结论 → 所在文件`。

**为什么不沿用旧编号**：裸数字在 30 个段里**各自从 1 重新起**（`### 1.` 出现 6 次以上），
不是唯一键；`E/W/D` 又是各次评审私有的前缀，不成体系。

### 归档文件命名

`<YYYY-MM-DD>--<来源类型>-<story key 或标记>.md`，来源类型 ∈ `cr`（code review）/
`ds`（story `[DS]`）/ `cs`（story `[CS]`）/ `决策` / `治理`。

例：`2026-10-12--cr-story-1-2.md`、`2026-10-22--cr-epic-1-集成层检视.md`。

## §4 分诊：逐条判

### 分诊单元的口径（先定这个，否则「逐条」无从执行）

本文件有两种条目形态，**重叠**：

| 形态 | 计数 | 分诊单元 |
|---|---|---|
| `### N. 标题` 小节型 | 201 个 | 一节 = 一条 |
| `- **标题** —— …` 顶层条目型 | 542 个 | 一条 = 一条（其下缩进的子项**不是**独立条目） |
| 回填表里的表格行 | —— | **不是**独立条目，是对原条目的结清记录 |
| 缩进的 `- ` 子项 | —— | **不是**独立条目 |

⚠️ 两个计数**互相重叠**（小节内部就是顶层条目），真实待办数须由脚本枚举后确定，
**不用 201 这个数当分诊基数**（那正是 R-37 的老坑：一个会自己烂掉的数字写进正文）。

### 判据

结论只有三个：`开放` / `已结` / `作废（前提被推翻）`。
判定顺序（**保守优先**）：

1. 顶部四批回填表逐条对照 —— 表里写 ✅ 的按表结清。
   ⚠️ **必须抽查表与原文是否脱节**（回填表可能指的是另一条）。
2. 条目正文自带结清标记（`✅ 已结` / `✅ 已关闭` / `✅ 已补` / 已作废）→ 已结。
3. 「前提不可达」但**写明**「将来 X 时会重新可达」→ 开放（待触发），
   恢复条件照抄那句。
4. 「仍未触发」/「恢复条件未成立」→ 开放（待触发）。
5. 「未裁决」/「等人定」→ 开放（待裁决）。
6. **找不到任何结清证据 → 开放**（默认开放，宁可留错也不误销）。

分诊结论**只落一处**：归档文件段尾的「分诊结论」小节，一行一条
`| 旧编号 | DF-ID | 结论 | 依据（原句） |`。**不另存一份分诊清单** —— 两份就是漂移源。

## §5 归档布局与文件构成

```
_bmad-output/archive/deferred/
  README.md                        # 索引 + 对照表 + 分诊统计 + 考古方法
  2026-10-15--回填表.md              # 顶部那 66 行「📎 回填表」本身（它是结清日志）
  2026-10-12--cr-story-1-2.md      # 一个 `## Deferred from:` 段 = 一个文件
  ...                              # 共 30 篇
```

每篇归档文件的构成：

1. **段首导语**（`>` 引用块）—— 逐字保留（它交代了这段是谁的哪一轮审查）。
2. **该段已结 / 作废条目的原文** —— 逐字保留，保留旧编号。
3. **段尾「分诊结论」小节** —— 见 §4。
4. **段尾「迁出条目」小节** —— 仍开放的条目**只留一行**：
   `| 旧编号 | DF-ID | 一句话 | 详情锚点 |`。

**原文唯一性**：每条原文恰好存在一处。
已结条目的原文在归档；开放条目的原文**搬到** `deferred-details.md`，
归档原位置留一行指针（不复制）。

**为什么按段切而不按月合并**：段内编号自洽（每段 1-6、26-34…），
合并会让编号失去上下文。30 个小文件都在「默认不读」的目录里，不构成成本。

**README 写法**照 `_bmad-output/archive/README.md` 的现成结构与口气：
「是什么 / 默认不要读这里 / 需要考古时怎么查 / 什么时候移进来 / 谁负责移进来」。

## §6 活账本与详情文件的格式

### 活账本 `deferred-work.md`

```markdown
# 延后工作（活账本）

> 本文件是**活账本**：只登记**仍然开放**的条目，每条一行。
> 登记格式见 `docs/rules/process.md` R-35；账本形态与归档分工见 R-43。
> 完整论证在 `deferred-details.md`；**已结**条目的历史在
> `_bmad-output/archive/deferred/`（默认不读，考古见该目录 README）。

## 条目

| ID | 状态 | 归属 | 恢复条件 | 一句话 | 详情 |
|----|------|------|---------|--------|------|
| DF-001 | 待裁决 | Story 3.2 | 拿到档位 3 门槛的产品裁决后 | `balance-sim` 门槛表头「16 回合上限」对 `maxTurns=10` 那一行不成立 | `deferred-details.md#df-001` |
```

字段约定：

- **状态**只有三个值，全算开放：`待裁决`（需人拍板）/ `待触发`（触发条件未成立，可机械判定）/
  `待排期`（无条件成立，只等排期）。
- **恢复条件**必须是**可判定**的一句话（沿用 R-35）。
- **一句话** ≤ 60 字，且**必须点名文件 / 函数**，否则它继承这批条目「不可证伪」的毛病。
- **详情**指向 `deferred-details.md` 的锚点，**不指行号**。

### 详情 `deferred-details.md`

```markdown
## DF-001

**状态**：待裁决 · **归属**：Story 3.2 · **恢复条件**：拿到档位 3 门槛的产品裁决后
**一句话**：`balance-sim` 门槛表头「16 回合上限」对 `maxTurns=10` 那一行不成立

### 原始论证

（原文逐字。来源标注：`## Deferred from: code review of story-2-3-阳光经济档位扩展 (2026-10-21)` 第 45 条）
```

锚点规则：`## DF-001` → `#df-001`（GitHub 风格小写连字符）。

## §7 规则改动

| 改动 | 内容 |
|---|---|
| **改写 R-35**（`docs/rules/process.md`） | 补上**登记格式**（ID/状态/归属/恢复条件/一句话/详情指针）、活账本只列开放项、已结归档、**引原句不引行号** |
| **新增 R-43** | 「延后账本只留开放条目」—— 活账本 / 详情 / 归档三层分工、归档触发条件、归档属于收尾动作 |
| **同步 `docs/rules/README.md`** | 索引表加 R-43 行、更新 R-35 的一行摘要与其「守卫」字段 |

**R-35 与 R-43 分开写**（而非合并）：R-35 管「**必须**登记」，R-43 管「登记之后长成什么样」。
后者要能单独被守卫覆盖。

⚠️ 规则正文**不写具体条目编号与条数**（R-37 的老坑：一个会自己烂掉的数字写进规则正文）。

⚠️ **R-35 本身仍然是「⚠️ 无守卫」** —— 「某个问题是否已登记」无法自动判定。
**不给它编一个永远为绿的守卫**来制造「已覆盖」的错觉（R-41 原文：
「写一个永远为绿的守卫比不写更坏」）。有守卫的是 **R-43**。
