## §0 裁决 —— 开工前已定，Dev 不必重新决定

### 裁决 1 —— 存储键与 `schemaVersion` 放**同一个值**里，不放键名里

**localStorage 键名在规划产物里是真空** —— `game-architecture.md` 决策 5 逐字只给了
`SaveFile` 的结构，`epics.md` AR14 逐字只给了同样的结构，**两份文档都没出现过任何键名**。

**定案：** 单键 `'plantsgame.save'`，值内含 `schemaVersion: 1`。

**为什么不是把版本编进键名（`plantsgame.save.v1`）：** 决策 5 的注释逐字写
「`schemaVersion: 1,      // 未来结构变更时迁移的依据`」，且逐字要求
「读取时校验 `schemaVersion`，不匹配则安全降级（提示重新开始，不得崩溃）」。
版本编进键名 ⇒ 旧键会**留在 localStorage 里变成垃圾**，且「不匹配就降级」这条判据永远走不到
（读的是新键，版本号天然一致）。FR61 逐字要求的是**校验**，那就得有一个能被校验的值。

**为什么键名带项目名前缀：** 本作部署在 `https://<host>/plantsgame/`（AC-11 / R-… base 守卫），
与其他应用同源；裸键名 `save` 会与同域其它应用撞车，撞车后果是**读到别人的存档**，
而 `JSON.parse` 恰好能过、结构恰好对得上（`currentGame` 为 null）⇒ **静默丢进度**。
这不是假想：守卫 G75/G76 要测的正是「结构合法但内容不认得」这一路。

### 裁决 3 —— 读档在 `enterLevel()` 里做，**不在模块求值期做**

**真空：** 规划产物没规定读档时机。候选是「模块求值期」与「进关时」。

**定案：`enterLevel()`。** 三条理由：

1. `state` 在 `store.ts` 的**模块求值期**就建好了（`state.ts` 里 `state = ref(initialState())`），
   读档要**替换** `state.value`。放模块顶层 ⇒ `initialState()` 白跑一次，
   而 `initialState()` 内部有 try/catch 与人话提示（「`[app]` 组装单元 1 的初始 state 失败：…」）——
   读档失败与建局失败会在同一行代码上混成两件事。
2. 读档是**「进入游戏」的一部分**，不是应用启动的一部分。StartView 的 `onStart`
   已经串好了音频解锁 → `enterLevel()`，那正是 GDD 逐字说的「重进」的入口。
3. 4-8 岁孩子每次都要点一次开始（音频解锁在那条链路上）；把「恢复」挂在那次点击之后，
   孩子不会看到任何技术动作。

⚠️ **连带口径**：`enterLevel` 现在逐字是「只改 `view` + 起 BGM」，读档后它还要多三件事
（喂 `state` / 喂 `progress` / 失败时回退）。**这不是违反 1.14 的注释** —— 那条注释说的是
「**不改 `state`**（`state` 在模块求值期就建好）」，本 story 正是要把那句话说清楚为什么不再成立。

### 裁决 4 —— `SAVE` effect 携带 `currentGame`，`progress` 经 `runEffectsFromStore` 第 4 参传入

**这是本 story 最容易写错的一处接线，逐字给死。**

现有形状：`store.applyAction` 第 3 步调
`runEffectsFromStore(action, prev, next)`，`runEffects(action, prev, next)` 是纯函数返回
`readonly Effect[]`，`runOne(effect)` 执行。1.14 逐字立的规矩是
「**判据（该播哪条 cue）全在 `core/effects.ts` 的 `runEffects` 里**，
播放实现在 `services/audio.ts` —— 三层各司其职，store 不碰「播什么」，也不碰「怎么播」」。

存档要写两样东西：**`progress`（独立 ref，不来自 dispatch）** 与 **`currentGame`（来自 `next`）**。
三个候选：

| 方案 | 判据位置 | 死在哪 |
|---|---|---|
| ① `SAVE` 保持无字段，runner 调 `writeSave(progress, next)` | runner | **`progress` 拿不到** ⇒ runner import store ⇒ 与 `store.ts → effects-runner.ts` 构成**循环依赖** |
| ② `SAVE` 携带 `progress` 与 `currentGame` | 纯函数 | `progress` 来自 store 的 ref，**不是** `(prev, next)` 能算出来的 ⇒ `runEffects` 不再是纯判据，且 `advanceProgress` 有「无增量返回入参」的性质，Effect 里会出现一个与 action 无关的对象 |
| ③ **`SAVE` 携带 `currentGame`；`progress` 由调用方传入** | 纯函数 | — ✅ |

**定案 ③：** `runEffectsFromStore(action, prev, next, progress)` 加第 4 参，
`runOne(effect, progress)`，`case 'SAVE'` 调 `writeSave(progress, effect.currentGame)`。

**为什么 `SAVE` 必须携带 `currentGame` 而不是让 runner 自己判断 `next.phase.kind`：** 因为
「局末 `currentGame` 置 `null`」是一条**判据**，1.14 逐字把判据划给纯函数了。
放 runner 就是第二份判据（R-37 的形状）。

⚠️ **代价，如实登记：** 这要**改动 1.14 已交付的 `src/core/effects.ts`** ——
把 `{ readonly kind: 'SAVE' }` 改成 `{ readonly kind: 'SAVE'; readonly currentGame: State | null }`。
连带必须做：

- 复跑 `npm run test`（1.14 的 `tests/core/effects.test.ts` / `tests/app/effects-runner.test.ts` /
  `tests/scaffold/effects-boundary.test.ts` 可能断言了 `SAVE` 无字段）；
- 更正 `1-14-音效与-bgm-接入.md` 里逐字写 `{ readonly kind: 'SAVE' }` 的 AC-B 段
  （**改判据、要留痕，见 R-57** —— 这是「文档追认事实」，不是偷偷改）；
- 更正 `deferred-work.md` 里 1.14 段第 2 条（那条 defer 逐字说
  「`case 'SAVE'` 在 1.15 会真的做 I/O，那时它抛错将**中断后续条目**」—— 本条由 AC-E5 处理）。

**`State` 进 `Effect` 不违 R-01：** R-01 禁的是 `core/` 里的**浏览器 API 与 Vue 符号**，
`State` 是本文件同层的纯数据类型，且 `State` 的 11 个字段逐字全是 JSON 可序列化的
（`src/core/types.ts` 的注释逐字说明 `grid` 刻意用字符串键而非 `Map`，就是为了这个）。

### 裁决 6 —— `SAVE` 的写盘点取 5 个相位里的 4 个（含一条 AC 内部张力的收口）

**真空 + 内部张力：** 1.15 的 AC 里有两句关于「什么时候写」：

- 「**Given** 玩法进行中 **When** 每个回合结束 **Then** 写一次存档（约 20-30 秒间隔）」；
- 「**And** 中途退出重进，能**精确恢复到上次答到的那一题**，**包括当前处于 `awaiting-build` 的局面**」。

⚠️ **这两句在「只在回合结束写」的字面读法下不可能同时成立。** 相位机是
`awaiting-answer → ANSWER → awaiting-build → PLACE_TOWER* → END_BUILD → resolving →
RESOLVE_ROUND → round-over`。若只在 `round-over` 写盘，则**存在 `awaiting-build` 的局面时
（孩子正挑着塔卡、或塔已放了还没点「开战」）磁盘上的存档永远是上一个 `round-over`** ——
后一句 AC 变成**构造上不可达**，也就是 1.14 AC-B6 专门守过的那种
「写了这个分支但构造上永远不产出」。更糟的是它**看起来被覆盖了**。

**定案（AC-C2 的表逐字照抄，别自己再推一遍）：**

| 相位 | 写不写 | `currentGame` 存什么 | 为什么 |
|---|---|---|---|
| `awaiting-answer` | ❌ 不写 | — | 刚 `CONTINUE` 出来，与上一份 `round-over` 存档内容相同；写它只是浪费一次 `setItem` |
| `awaiting-build` | ✅ 写 | `next` | 后半句 AC 要求的可恢复边界；也是 FR53 逐字「回合内的两处无限等待必须属于 State」在存档侧的落点 |
| `resolving` | ❌ 不写 | — | 真实一帧，`END_BUILD` 只切 phase，用户看不到也退不出 |
| `round-over` | ✅ 写 | `next` | 「每个回合结束」的主路径 |
| `level-failed` | ✅ 写 | `next` | 同样是 `applyResolve` 的出口。**不写的话失败后退出重进会退回上一个 `round-over`，那一局白打** |
| `level-complete` | ✅ 写 | **`null`** | 「战场被清空 ⇒ `currentGame` 置 `null`，`progress` 不受影响」。存 null 而非那个空战场 state：重进回到该单元起点，而不是一个**1.16 还没做的**「通关画面」终态 |

⚠️ **关于「约 20-30 秒间隔」：那是 GDD 对**答题节奏**的描述，不是计时器。**
AC 逐字「足够密集以满足断点续学，又不至于每次点击都写」，而按相位写盘天然满足 ——
`localStorage.setItem` 是同步 API，每回合 2 次（`awaiting-build` + `round-over`），
量级在每分钟几次。**本 story 不引入任何定时器。**

### 裁决 7 —— `save.ts` 的导出面：先例对齐 `services/audio.ts` 的降级面

1.14 逐字立的先例：

```ts
export type AudioDegradationScope = 'session' | 'asset'
export interface AudioDegradation { readonly scope: AudioDegradationScope; readonly key: string; readonly reason: string }
export function isAudioSilent(): boolean
export function audioDegradations(): readonly AudioDegradation[]
```

Story 1.17 逐字要「一次性列出所有正在生效的降级项**及其原因**」——
所以只有 `degraded: boolean` 不够用，**必须有结构化列表 + 原因**。存档照抄这个形状（AC-B4）。
`SAVE_KEY` 与 `SAVE_SCHEMA_VERSION` 也导出（守卫要读它们，见 AC-G1）。

### 裁决 8 —— 损坏 / 版本不匹配的降级**不留痕**：不动既有 key，直接返回 `null`

1.15 的 AC 逐字：「**Given** 游戏结束时仍未成功写入 … 上一次成功写入的存档仍可读取，
**不损坏既有存档**」与「**And** 存档文件损坏时同样安全降级为『从上一个单元重新开始』，
而非崩溃或卡死」。

⇒ `readSave()` 遇到 JSON 解析失败或版本不匹配时：**返回 `null`、登记降级项、保留原始字符串不动**。
**不许**顺手把那个 key 删掉或覆写 —— 「返回 null 但不清现场景」让「存档坏了」这件事
在 1.17 的调试面板里**仍然查得到**（降级项在），而删掉之后连证据都没了。
`clearSave()` 作为独立导出留给 1.17 的「重置进度」，本 story 内部不调用它。

### 现有代码逐字速查（Dev **必读**，不要凭记忆）

- **`src/core/types.ts` 的 `State` 有 11 个字段，全部 `readonly`，全部 JSON 可序列化**
  （`unitNumber` / `phase` / `turn` / `hearts` / `sun` / `grid` / `towers` / `zombies` /
  `deck` / `masteredEntryIds` / `unlocked`）。
  文件里逐字说明 `grid` 刻意用 `Readonly<Record<string, string>>` 而非 `Map`，
  理由就是 `Map` 能被 JSON 化成 `{}` —— **这条设计就是为 1.15 做的。**
- **`src/core/grid.ts` 的 `cellKey(row, col)` 返回 `"行,列"`**（如 `"2,4"`），文件头逐字说明
  **刻意不加前缀**，「以免将来序列化进存档时键格式变更作废全部存档」。
  ⇒ **`grid` 的键格式被架构注释保护着，不要动。**
- **`src/core/hud.ts` 的 `Progress`** —— 键名锁定点，`currentUnitIndex` **0 基**（裁决 2 / AC-B2）。
- **`src/core/effects.ts` 的 `runEffects(action, prev, next)`** —— 纯函数，
  返回数组的**顺序即执行顺序**，末尾的 `assertNeverEffect` 是编译期穷尽性兜底。
- **`src/app/effects-runner.ts` 的 `runEffectsFromStore(action, prev, next)`** ——
  逐字「**本函数绝不抛**……某一条抛错只记 `[audio] WARN` 并**继续执行后续条目**」。
  ⚠️ 那条 WARN 的前缀写死成 `[audio]`；存档失败那条必须是 `[save]`（AC-B6）——
  **不要**为了复用一个常量而把 `[audio]` 泛化，1.14 的守卫钉的就是 `[audio]`。
- **`src/app/store.ts` 的 `applyAction` 四步顺序不可换**；第 3 步（1.14 接的）在
  `state.value = next` **之前**，第 4、5 行（1.12 / 1.13 接的）在**之后**。
- **`src/content/index.ts` 的 `getUnit` / `entriesOf` 取不到单元就 `throw`**（AC-D3 的对象）。
- **没有任何 `router.ts`、没有任何 `src/components/debug/`** —— 别去 import 它们。

### ⚠️ 三条最容易照抄错的既有代码

1. **`advanceProgress` 在没有增量时返回入参本身**（1.13 AC-B3 第三条性质）。
   ⇒ `progress.value` **绝大多数 dispatch 上不产生引用变更**。
   若你在 1.15 里写了 `watch(progress, …)` 之类依赖引用变更的逻辑，
   它在大部分回合上**根本不会触发** —— 而那恰好是「回合结束」之外的绝大多数时刻。
2. **`awaiting-build` 的 `phase.unlocked` / `phase.sun` 是 `State` 同名字段的只读镜像**，
   由 `assertPhaseMirror` 断言恒等。恢复存档时**两份都要在**（AC-D2），
   只还原 `State` 的字段会让 `assertInvariants` 当场抛。
3. **`assertPhaseMirror` / `assertGridAndTowers` 这类不变量断言在合法状态空间内不可违**，
   但**来自磁盘的数据不在那个空间里** ⇒ 1.15 是**第一次**让外部数据流进 `reduce`/`assertInvariants`。
   这条要在 Dev Notes 里点明：`core/` 逐字「必须 `throw`，禁止 catch」那条（NFR12 第一层）
   在 1.15 之后多了一层意思 —— **不变量该抛仍要抛，是 app/services 层去接住它并降级**，
   不是让 `core/` 学会不抛。

### 关于「最新技术信息」这一项：本 story 为什么没有联网查

`localStorage` 的 API 形状十年来没变，且本仓库的技术栈里**没有引入任何新依赖的需要** ——
存档是 `JSON.stringify` + `setItem`/`getItem`，不需要 idb、pinia-plugin-persist、
或任何持久化库（R-38：装依赖是项目级决定，需要时先问）。
⚠️ **不要**顺手装一个持久化库来「省事」。
