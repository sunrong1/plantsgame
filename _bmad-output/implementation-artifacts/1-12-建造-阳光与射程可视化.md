# Story 1.12: 建造、阳光与射程可视化

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 孩子,
I want 答对换来的阳光能变成一株看得见的防线，并且落子前就看得见它能打多远，
So that 我是在打僵尸，而不是在猜规则。

## §0 五条裁决（2026-10-15 `[CS]` 落定，**不得在本 story 内推翻**）

### 裁决 1 —— 射程预览画**真实伤害形状**，不是「半径 3 的圆」

**冲突的事实（这是本 story 最重的发现，不是风格问题）：**

| 来源 | 说的是什么 |
|---|---|
| `epics.md:1134` / `game-architecture.md:245-246` / `gdd.md:351` | 放置预览 = **半径 3 的圆（含斜向）**，且范围塔「与直射塔一致」 |
| `gdd.md:337` / `epics.md:1014` | 「塔的射程是圆形覆盖，因此**种在上下相邻行的塔也能打到中间行**」 |
| **`src/core/turn.ts:82`（实际代码）** | `towers.filter((tower) => tower.row === ZOMBIE_ROW)` —— **只有第 3 行的塔开火** |

⇒ **第 2/4 行的塔整局一枪不开**，而上面三条文档都说它们能打。没有人显式裁决过
「相邻行的塔是哑炮」—— 它是从「战斗原语只收列号、不收行号」这个设计里**长出来的**
（`combat.ts:19-23` [CR] D4 裁决只裁了「行过滤住在哪一层」，没裁「过滤掉什么」）。

**裁决内容：**

1. **预览集合 = 「若把塔种在 (row, col)，它实际能打到哪些格子」**，逐字复用 core 的既有判据：
   - 前置 `row === ZOMBIE_ROW`（`turn.ts:82`）
   - `direct` / `slow`：`inRange(col, c, rangeOf(towerType))`，即第 3 行的 `[col+1, col+range]` ∩ 网格
   - `aoe`：`aoeColumns(col)`，即第 3 行的 `[col-1, col, col+1]` ∩ 网格
   - 落在第 3 行之外 ⇒ **集合为空**
2. **非第 3 行在选中卡时整行压暗**，与「不可建格」的压暗**形状相反**（横带 vs 竖带），
   让孩子从画面直接读出「僵尸只走中间那一行」，而不是靠文字说明。
3. **登记作废 / 消歧**（Dev 收尾时写进 `deferred-work.md`）：
   - `game-architecture.md:245-246`「放置覆盖：半径 3 的圆」—— **作废**，理由记 `[CC]`
   - `gdd.md:337` / `:351` —— 登记为**已被实现消歧**（以 `turn.ts:82` 为准）
   - `epics.md:1014`「种在上下相邻行的塔也能打到中间行」—— 登记为**已被实现消歧**
   - `epics.md:1134`「范围塔须能同时画两套形状」—— **改判据**，见下方偏离登记

> **为什么不让实现去迁就文档：** 改「相邻行能不能开火」是**战斗判定变更**，
> `tests/core/assertions.test.ts` 的 5 条数值断言与 `npm run balance-sim` 的门槛数字
> 都要重跑，而 Story 1.19（Epic 1 生死线）就建立在那些门槛数字上。
> 「实测值优先于文档值」是本仓库反复付过学费定下的做法（1.11 的 `--text-option` 实测推翻了两次估算）。
> 若日后要让相邻行开火，那是 `[CC]` + 1.19 重验的事，不是 UI story 顺手带的事。

### 裁决 2 —— 手牌区**横向滚动**，按解锁顺序

单元 1 共 **37 个词条**（`unit-01.json`：`direct 13 / slow 13 / aoe 11`），答对一个解锁一张卡，
而网格只有 **35 个可建格**。因此手牌区**必然**要能装下十几张卡。

- 卡面 = **塔图 + 单词文字 + 造价数字**（三者都要，见 AC-C2）
- 横向排列，`overflow-x: auto`，卡宽 **132px**、档间距 **12px**、**高度不钉死**
  ⇒ 若卡区能占满 768px 则放下 **5 张整卡 + 第 6 张露出 48px**
  （768 − 5×132 − 4×12 = 60，再扣一个 gap 剩 48）
  ⚠️ **但「⚔ 开战」按钮与卡区同排** ⇒ 真实首屏张数要减掉按钮宽。
  **这个数不是拍出来的** —— AC-H1-3 要求真浏览器量出按钮宽后再套
  「整卡数 = ⌊(卡区宽+12)/144⌋」。上面那个 48px 只是**上界**。
  「露头」是刻意的：它告诉孩子右边还有卡。
- 顺序 = `state.unlocked` 的顺序（= 解锁顺序 = 答对顺序），**不重排、不分组**

### 裁决 3 —— 「结束建造 → 结算 → 下一题」的推进链路归 1.12，加一个「开战」按钮

**为什么必须落在 1.12：** 现状是 `applyAnswer` 答完立刻切到 `awaiting-build`（`reducer.ts:195`），
而**没有任何 story 拥有 `END_BUILD` 之后的那段链路**（1.13 管 HUD/effects-runner，
1.16 管通关/失败/重打，两者的 AC 里都没有「结算这一回合」）。
不接上它，1.12 交付后游戏停在 `awaiting-build` —— **1.12 的成果无法真机验证**。

- 手牌区右侧常驻一个「⚔ 开战」按钮，**只在 `phase.kind === 'awaiting-build'` 可用**
- 点击一次依次 dispatch：`endBuild()` → `resolveRound()` → **`phase.kind === 'round-over'` 时**才 `continueRound()`
- 终态（`level-failed` / `level-complete`）**不 dispatch `CONTINUE`**，
  且本 story **不渲染**终态画面（属 1.16）—— 见 AC-F4 的边界条款

### 裁决 4 —— 覆盖预览挂在「`pointerdown` 指向的那一格」上，不是选中卡就铺满所有空格

`epics.md:1133` 只说「空格子要能叠半透明覆盖层」，**从没规定何时显示**。
原 AC 写「选中一张卡时，所有空格子以半透明色块显示射程覆盖」—— **这句话有两个洞**：

1. **它在数学上退化**：第 3 行 7 个可建格的覆盖并集 = **整行全亮**，
   等于什么都没告诉孩子；而「所有空格子」这个说法**也给不出坐标** ——
   `coverCellsAt(row, col, type)` 需要一个具体的 `(row, col)`。
2. **目标形态没有 hover**（竖屏平板，`gdd.md:557`），「选中即显示」必须有个落点。

**裁决内容：指向（candidate）= 已选中卡 + 手指/鼠标按在某个格子上（`pointerdown`）。**

- 按在**可建空格** ⇒ 该格与 `coverCellsAt(row, col, towerType)` 的每一格加 class `.is-in-range`；
  `pointerup` 落在**同一格** ⇒ 种下；落在别处 ⇒ **只移动预览、不种**（守卫 G41 / 变异 M74）。
- 按在**已占用格 / 不可建格** ⇒ 不画覆盖，走 AC-D3 的压暗闪。
- 选中但**尚未指向任何格** ⇒ 只画 AC-E3 的非僵尸行压暗，不画 `.is-in-range`。
- 用 `pointerdown`/`pointerup`，**不用 hover、不用拖拽**（`pointermove` 被守卫 G39 明令禁止）；
  竖屏平板上「按下去先看见射程、抬手才种下」正是标准做法。
- ⚠️ **指向格自己不算覆盖**：`.is-in-range` 逐字等于 `coverCellsAt` 的返回值，
  `aoe` 含自身、`direct`/`slow` 不含 —— UI 不得额外点亮它，否则与 `aoe` 语义打架。
  指向格用另一套视觉 `.is-candidate`。

### 裁决 5 —— 手牌卡的单词文字 = `promptText` **全文**，一律不裁成 slug

**这是 `[CS]` 校验阶段抓出来的洞，不是风格问题。** `epics.md:1101-1137` 只说「塔卡出现在手牌区」，
**从没规定卡面上写什么**；而 `DeckEntry`（`types.ts:273-280`）只有
`{ entryId, wordId, towerType, card }`，**没有任何「短显示名」字段**。

先说被否掉的那条路（原 AC-C2 的写法）：`wordId` 去掉 `u1-` 前缀。
单元 1 实测（`unit-01.json`，37 词条 = `word 30 / response 6 / keyword 1`）：

```
word     30 张：wordId == promptText 化简（"Hello" → "u1-hello"），最长 "beautiful"（9 字符）
response  6 张：wordId = 句子 slug —— "Good morning!" → "u1-s-good-morning"（12 字符）
keyword  1 张 ：wordId = 句子 slug —— "I have a ball for my dog." → "u1-s-i-have-a-ball-for-my-dog"（26 字符）
```

⇒ 那条路会让**最长的 label 变成 26 字符**，是 `beautiful` 的 2.9 倍，
把 AC-C3 的整套宽度推导（112px 可用宽 / 16% 余量）当场推翻。
更糟的是它**在卡面上显示一个孩子从没见过的机器 slug**（`s-i-have-a-ball-for-my-dog`）——
卡面应当是「你答对了这句话」，不是它的文件名。

**裁决内容：`label = card.promptText` 全文，一个规则覆盖全部 37 张，不分卡型。**

- 单词卡自然是一行；短句卡（最长 25 字符）**允许折成两行**，
  卡面高度随行数走 —— 手牌区**不钉死高度**（`1-11:904` 的同一条纪律）。
- 渲染用 `white-space: normal` + 最多两行的行钳；**不允许省略号截断单词**，
  **不允许为了塞进去缩到 `--text-body: 16px` 以下**。
- 若实测两行仍装不下 ⇒ 记一条**如实降级**并把结论移交（AC-C3 / AC-H1-4），
  **不许**在本 story 内改词条 JSON（那属 Epic 2 的内容层，且 `CLAUDE.md` 明令词条 JSON 不擅动）。
- ⚠️ 这条是**产品决定**（孩子界面上出现什么字），落在这里是为了让 AC-C3 / AC-B5 / AC-H1-4
  能被写出可测的判据；**若你认为该走别的口径（如新增数据字段），请推翻本裁决并改这三处 AC**。

## ⚡ 给 Dev 的 60 秒速读

1. **本 story 不碰任何战斗数值**。所有造价 / 射程 / 阳光判定一律走 `core/` 新函数。
2. **组件不许 import `core/balance`**（ESLint 已配，`eslint.config.js:172-190`）——
   造价数字必须由 `core/build.ts` 的判据返回。这是本 story 最容易撞的架构红线。
3. **「能不能放」只有一份判断**：`core/build.ts` 的 `placementBlockedReason()`，
   与 `reducer.placeTowerIn()` 的 8 行规则逐条对齐，并由交叉断言测试守着。
   组件层**绝不自己写第二份**。
4. **射程覆盖 = 真实伤害形状**（裁决 1），且**挂在 `pointerdown` 指向的那一格上**（AC-E1）——
   不是「选中卡就铺满所有空格」（那在数学上退化成整行全亮）。第 3 行之外不画覆盖，改画整行压暗。
5. **卡面单词 = `promptText` 全文**（裁决 5），**绝不**用 `wordId` 去前缀 —— 那会渲染出
   `s-i-have-a-ball-for-my-dog` 这种 26 字符的机器 slug。
6. **「开战」按钮** dispatch 三连（裁决 3），且 `CONTINUE` 前必须判 `round-over`。
7. **守卫从 G30 起、变异从 M57 起**（现状 G1–G29 / M1–M56，动手前先 `grep -rho "G[0-9]\+" tests/ src/ | sort -uV | tail` 再确认一次）。
8. **真浏览器必查**：射程覆盖层 / 整行压暗 / 手牌卡横滚 / 造价数字 —— jsdom 的 `clientWidth` 恒为 0。
9. **每加一个 `.vue` 就跑一次 `npm run typecheck`** —— vitest 走 esbuild，不做类型检查，**全绿而 typecheck 红**是本仓库实测过的形态。

7. **tsv 不做类型检查** —— vitest 走 esbuild，**每加一个 `.vue` 就跑 `npm run typecheck`**

9. **`grep` 用 `-F` 不用 `-E`** —— `()` 被当分组符会误报「变异没落上」（1.5 白跑 5 项）
